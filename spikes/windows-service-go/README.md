# `murmur-svc` — адаптер службы Windows

Демон Murmur это node-процесс, а диспетчер служб Windows запускает только программу,
которая отвечает ему на управляющие сообщения. `node.exe` на них не отвечает, поэтому
между SCM и демоном нужен хост — то, чем для чужих программ служит NSSM. Здесь он свой,
потому что обязан отдавать наружу то, чего сегодняшняя задача Планировщика не отдаёт:
состояние, pid, время старта и код выхода.

Бинарь предназначен для адаптера CLI (`murmur service install|start|stop|status`).
Подключение к CLI — отдельная интеграция; наличие этого бинаря само по себе её не доказывает.
Сам хост в протокол не лезет и про NATS ничего не знает.

## Команды

```
murmur-svc install     # создаёт службу, требует прав администратора
murmur-svc uninstall
murmur-svc start
murmur-svc stop
murmur-svc status      # JSON, поле service из CONTRACT.md
```

Человеческие сообщения по умолчанию английские. Для прямого запуска помощника доступен
ограниченный переключатель `--lang en|ru`, например `murmur-svc --lang ru start`.
Переменные окружения на язык не влияют. Выбранный язык действует только на этот запуск;
JSON-схема, коды состояний и причины с префиксом `service.` не меняются. Запись службы в
SCM сохраняет прежнюю строку `run <serviceName>` без языкового аргумента, поэтому фоновый
`service.log` остаётся английским. Оба JSON-каталога встроены в один exe.

При отказе последняя строка stderr имеет машинный формат
`murmur-svc: reason=<key>` с завершающим LF. Ключ — проверенный ключ встроенного
каталога (`[A-Za-z][A-Za-z0-9.]*`), одинаковый для EN/RU; неизвестная нетипизированная
ошибка даёт `error.unknown`. Человеческий текст перед ним и коды выхода сохранены.
После успешного отката передаётся исходная причина запуска, например
`daemon.didNotLive`; неудачный откат имеет приоритет `install.rollbackFailed`.
CLI должен разбирать только эту последнюю строку, а не искать похожий текст в
произвольном stderr, который может содержать пути и сообщения ОС. Подробности
остаются в диагностике и журналах; сам footer не включает их. `--version` и другие
успешные команды footer не печатают.

`install` читает окружение:

| переменная | что | по умолчанию |
|---|---|---|
| `MURMUR_NODE` | путь к `node.exe` | `node` из PATH |
| `MURMUR_ENTRY` | путь к `scripts/murmur-daemon.mjs` | обязателен |
| `MURMUR_WORKDIR` | рабочий каталог демона | родитель каталога `MURMUR_ENTRY` |
| `MURMUR_SERVICE_NAME` | имя службы | `MurmurDaemon` |
| `DATA_DIR` | закрытый каталог личности и базы | `.data` внутри рабочего каталога |

Все пути обязаны быть абсолютными: служба стартует с рабочим каталогом `System32`, и
относительный путь означает там совсем другой файл. `install` проверяет это сам и
отказывается ставить службу, которая не запустится.

## Где что лежит

```
%ProgramData%\Murmur\<имя службы>.json          описание запуска
%ProgramData%\Murmur\<имя службы>.state.json    история с pid хоста и началом окна
%ProgramData%\Murmur\logs\<имя службы>\daemon.log    stdout и stderr демона
%ProgramData%\Murmur\logs\<имя службы>\service.log   решения надзора
```

Это общедоступные для чтения метаданные службы. Закрытый `DATA_DIR` с ключами
хранится отдельно: пересечение с `%ProgramData%\Murmur` в любую сторону запрещено
до изменения каталогов и ACL. Служба получает абсолютный путь к профилю.

Логи в UTF-8. `Get-Content` в PowerShell 5.1 читает их кодовой страницей ANSI и портит
кириллицу — нужен `-Encoding UTF8`.

## Надзор

Упавший демон перезапускается с паузой, растущей от 2 до 60 секунд. Прожил дольше
тридцати секунд — пауза сбрасывается. Растущая пауза здесь не украшение: демон,
падающий из-за отозванного токена, частыми перезапусками не чинится и не должен
молотить брокер.

Остановка службы снимает дочерний процесс: Windows не знает сигналов, поэтому это
`Kill`. Демон переживает это штатно — незавершённое лежит в SQLite, не в памяти.

## Приёмка, пройденная вживую

Проверено на временной службе `MurmurSpikeTest` с заглушкой вместо демона, чтобы не
трогать работающий контур:

| проверка | итог |
|---|---|
| `install` без прав администратора | внятный отказ, службы нет |
| `install` без `MURMUR_ENTRY` | отказ с названной причиной |
| `start` → `status` | `running`, pid дочернего процесса, `since` заполнен |
| дочерний процесс убит извне | надзор поднял новый через 2 с, запись в `service.log` |
| `stop` | служба остановлена, дочерний процесс снят |
| `uninstall` | служба удалена из SCM |

**Не проверено:** переживание перезагрузки ОС. Тип запуска `StartAutomatic` выставлен,
но ребута на этой машине не было — за проверенное не выдаю.

## Правки по ревью 19.09, вечер

**Установка заканчивается проверкой, а не записью в SCM.** `install` создаёт службу,
запускает её, ждёт устойчивого `Running`, дожидается появления демона и убеждается, что
демон прожил шесть секунд. Не подтвердилось — служба останавливается и удаляется, и в
системе не остаётся половины. Нулевой код теперь означает работающую систему.

То же у `start`: запрос диспетчеру не есть факт запуска, поэтому состояние опрашивается
до устойчивого `Running` или до внятного отказа с таймаутом.

**Отказ доезжает до диспетчера.** Надзор, который не может поднять демона, раньше молча
выходил, и служба выглядела остановленной по желанию человека. Теперь `Execute` уходит
со служебным кодом: `10` — описание запуска не прочитано, `11` — демон не запускается,
`12` — падение по кругу, `13` — каталог логов недоступен. `status` читает служебный код
и отдаёт `failed`, иначе правилу «серый выигрывает у красного» неоткуда взять красный.

**Перезапуски считаются.** Пять подъёмов за час по умолчанию — это падение по кругу, а не
работа: надзор сдаётся, служба уходит в `failed`. В статусе появились
`restartsLastHour`, `lastExitCode` и `lastFailureAt`; неизвестное отдаётся как `null`,
никогда как ноль и никогда как пустая строка.

**Права каталога данных закрыты явно.** Проверено на живой машине: свежий подкаталог
`%ProgramData%` наследует `BUILTIN\Users:(CI)(WD,AD,WEA,WA)` и `CREATOR OWNER:(F)`. Файл
с описанием запуска там может ещё не существовать, а значит обычный пользователь вправе
создать его первым и стать владельцем с полным доступом. Служба исполняет указанный в
нём путь под `SYSTEM` — это прямое локальное повышение привилегий. Теперь `install`
задаёт DACL явно и с запретом наследования (`SYSTEM` и администраторы — полный доступ,
остальные — чтение), удаляет файл, который мог быть создан до установки, и пишет свой
заново. Служба перед чтением сверяет владельца файла и отказывается работать, если это
не система и не администраторы.

После правки `icacls %ProgramData%\Murmur` показывает три строки: `SYSTEM:(OI)(CI)(F)`,
`Administrators:(OI)(CI)(F)`, `Users:(OI)(CI)(RX)`.

### Приёмка правок, пройдена вживую

| проверка | итог |
|---|---|
| установка с живым демоном | пошаговый вывод, подтверждение, код 0 |
| установка с демоном, падающим сразу | отказ с причиной, откат, служба удалена, код 1 |
| `status` после отката | `lastExitCode: 3`, `restartsLastHour: 2`, `manager: none` |
| права каталога после установки | наследование снято, запись только у системы и администраторов |

Временная служба и каталог данных после приёмки удалены, работающая задача Планировщика
не тронута.

## Правка по второму ревью

Сообщение отката говорило «в системе ничего не осталось», и это было шире факта:
каталог данных и файл запуска пишутся до создания службы и откат переживают. Теперь
отказ перечисляет поимённо, что осталось и зачем — журнал нужен для разбора.

Эта же правка вскрыла вторую половину: откат советовал `murmur-svc uninstall`, а тот
отказывался работать, когда службы в диспетчере уже нет, то есть ровно в том случае,
ради которого его и советовали. Теперь `uninstall` убирает файлы и без записи в
диспетчере, а журнал оставляет намеренно и говорит об этом.

Каталог логов на продукт теперь один — `%ProgramData%\Murmur\logs`. Человек, которому
сказали «пришли журнал», должен идти в одно место.

## Контрревью движка: пять правок

**Каталог данных стал явным.** В описании запуска появился абсолютный `dataDir`, и он же
уезжает в окружение дочернего процесса. Имя переменной проверено по исходнику:
`scripts/murmur-daemon.mjs` читает `DATA_DIR` и без неё берёт `.data` относительно
рабочего каталога. `DATA_DIR` — каноническое имя текущей версии; `MURMUR_DATA_DIR` передаётся
рядом только для совместимости. Разные значения двух имён отвергаются.

**Путь хранилища заполняется только свидетельством.** В ответе появились
`observedStorePath` и `observedStoreUnknownReason`. Свидетельство берётся у диспетчера
перезапуска Windows: он отвечает, какие процессы держат файл открытым. Совпал pid нашего
демона — путь заполняется, иначе остаётся пустым с названной причиной. Из описания
запуска и окружения путь не выводится: они говорят, чего мы просили.

Проверено на живом демоне, а не на заглушке: процесс `node` под задачей Планировщика
опознан как держатель `C:\Users\Administrator\murmur\.data\murmur.db`, а подстановка
чужого pid свидетельства не даёт.

**Счётчик перезапусков обнуляем.** Ноль означает «подъёмов не было», непрочитанное
состояние — `null` и `restartsUnknownReason`.

**Порог перезапусков приходит из описания запуска**, значение по умолчанию пять. Так
значок и движок не разъедутся при его изменении.

**Владение профилем проверяется** перед установкой, стартом, остановкой и удалением:
программа службы обязана быть этим бинарём. Имя службы задаётся снаружи, значит
совпадение с чужой возможно, и без проверки мы однажды остановим чужое. Чужая служба
отдаётся в статусе как `manager: foreign` с названной причиной.

## Правка порядка в установке

Проверка «служба уже установлена» стояла на двадцать строк ниже, чем перезапись описания
запуска и удаление состояния. Команда честно отказывала и к этому моменту уже портила
файлы работающей службы: код возврата был верным, врало состояние на диске.

Теперь решение о том, состоится ли установка, принимается до единого изменения на диске:
сначала диспетчер служб и проверка владения профилем, затем всё остальное. Регрессия
проверяет содержимое файлов побайтово, а не код возврата.

**Проверка владельца заменена проверкой прав, и нашла это собственная регрессия.** Файл,
созданный администратором из-под своей учётной записи, принадлежит этой учётной записи, а
не группе администраторов, — прежняя проверка отвергала обычную установку. Значение имеет
не владелец, а то, есть ли право записи у кого-то вне системы и администраторов. Теперь
разбирается список доступа. Отдельный тест подтверждает, что проверка умеет отказывать:
файл с правом записи для всех признаётся недоверенным.

**pid хоста службы и pid демона разведены.** В статусе появилось поле `daemonPid`:
вопрос «жив ли демон» относится к дочернему процессу, а не к процессу, который им
управляет.

**Порог перезапусков сравнивается по «больше или равно».** Пять подъёмов за час — это уже
падение по кругу, а не последний нормальный случай.

## Интеграция и приёмка на чистой Windows

`status` требует только прав запроса к SCM и конкретной службе; обычный пользователь
может наблюдать её без повышения прав. Установка, запуск, остановка и удаление по-прежнему
требуют администратора. ImagePath разбирается штатным Windows-разбором командной строки,
затем сверяются файл программы и аргументы `run <serviceName>`. Пробелы в `Program Files`
не превращают собственную службу в чужую.

Ответ имеет схему `murmur.windows-service/1`. `profile` содержит проверенное описание
запуска; `pid` относится к хосту SCM, `daemonPid` — к дочернему процессу. CLI должен
передавать ожидаемые `DATA_DIR`, `MURMUR_NODE`, `MURMUR_ENTRY`, `MURMUR_WORKDIR` при каждом
действии. Несовпадение закрывает и чтение наблюдений, и мутацию. Чтение и последующее
действие не являются одной атомарной операцией.

`restartCount` измерен только в `restartWindowMs`, начиная с запуска текущего
подтверждённого SCM-хоста. До полного часа `restartsLastHour` остаётся `null` с
`service.history-window-incomplete`; удалённая или старая история не означает ноль.
Повторный `start` проверяет уже работающий процесс, не удаляя свидетельство его PID.
`uninstall` отказывается удалять службу, которую не удалось остановить.

Регрессия с `MURMUR_SVC_E2E=1` ставит отдельную службу и проверяет повторную установку,
повторный запуск, отказ остановки чужого выбранного профиля, неизменность spec/state/PID
и неполное окно истории. В обычном CI этот тест пропускается. Go test на Windows —
отдельное свидетельство от приёмки настоящего демона, обмена и перезагрузки ОС.
